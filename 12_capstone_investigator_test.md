# Module 12 — Capstone: the `investigator` Skill and its behaviour test

Part of the Root-Cause Analysis Playbook. Program and progress: [CURRICULUM.md](CURRICULUM.md).

## The answer first

A **Skill** is an instruction file that an AI assistant loads for one kind of task. The `investigator` Skill tells it how to run a root-cause investigation, using this playbook.

**Conclusion: the Skill passed its test.** The test's rules were written down before any run (a pre-registration). Across 6 new root-cause cases, the assistant with the Skill scored higher than the same assistant without it in **all 6 cases**, against a bar of at least 5. Two graders scored the reports independently, without knowing which reports used the Skill, and under both graders' scores the result was 6 of 6.

**What it improved, and what this test could not show:**
- **How the investigation was run: a clear improvement.** With the Skill, the assistant more often named a fitting technique, wrote a clean problem statement, and proposed a full control: what to monitor, the limit, and the response.
- **Finding the cause: not shown.** Both versions found the cause built into the data in all 24 runs. The cases were too easy to tell whether the Skill helps find causes.

## 1. What the Skill does

It is a decision layer on top of the playbook, not a copy of it. When the assistant gets a root-cause question, the Skill has it:
1. **Check the data first:** what each row is, the date range, partial periods, and what the data cannot say.
2. **Decide what kind of problem this is, and pick the framework:**
   - an incident that is hurting someone now → 8D (Eight Disciplines, Module 11)
   - a long-standing gap → DMAIC (Define, Measure, Analyze, Improve, Control, Module 1)
   - a question about future risks → FMEA (Failure Mode and Effects Analysis, Module 10)
   - "why did nothing stop it?" → barrier analysis (Module 9)
3. **Pick the technique** from a table that maps each kind of problem to a technique and its notebook (Modules 2 to 10).
4. **Run it to the playbook's standards.** There are 12 rules. Among them:
   - write the problem statement before asking why
   - check the problem is real before explaining it
   - tag every finding: an Observation is what the data shows, a Hypothesis is an untested explanation, a Conclusion follows from what is shown
   - end with a fix and a control
5. **Stop at a verified cause, or at named hypotheses** with the evidence that would settle each.

If the user names a technique ("use the 5 Whys"), the Skill follows it, and says once if another would fit better.

It is installed in the user's personal Skills folder (`~/.claude/skills/investigator/SKILL.md`). The installed file is now version 1.1 (section 7). The version tested here is kept as a frozen copy.

## 2. The test design

The design below was written down before any run. The pilot (end of this section) changed four details of how runs were set up and graded, all listed in Section 3. It did not change the cases, the scoring sheet or the success rule.

### The question

Given the same problem and the same data, does the assistant with the Skill produce a better root-cause investigation than without it?

### The two arms

- **Plain arm:** a new assistant session, with no memory of the other runs, gets the case brief and the path to the case data.
- **Skill arm:** the same, with one extra first line: "First read and follow the Skill at …".

The model and the tools were the same, and each run had its own folder with only its case's files. **One difference beyond the instruction itself:** the Skill arm was allowed to open the playbook notebooks the Skill points to, and the plain arm was not. 10 of the 12 Skill-arm reports cite a notebook. So the Skill arm had more reference material, not only instructions.

The Skill was not installed during the test, so the plain arm could not find it.

### The 6 cases

Each case has a short brief, a simulated dataset (generated by code that gives the same data every time), and a **planted cause**: the cause deliberately built into the data, written down and kept hidden from the runs. None reuses a curriculum dataset.

| case | the brief, as given | the planted cause | the technique that fits |
|---|---|---|---|
| C1 | "Trial-to-paid conversion for our SaaS product has dropped. Find out why." (SaaS = software as a service) | from one date, only EU customers, only at the billing step, where a field for VAT (value-added tax) was added. A marketing email the same week is a decoy | is / is-not and change analysis: mark where the problem is and is not, then what changed there (Module 4) |
| C2 | "Support is drowning in tickets. Which problem should engineering fix first?" | the most common ticket type is cheap. A rare one ("data export fails") costs the most time and blocks the most customers | Pareto, by count and by impact: rank the types both ways (Module 2) |
| C3 | "A 100%-off discount code went live by mistake and was used more than a thousand times. How do we make sure this can't happen again?" | five defences: two missing, two failed, and one worked late (a daily finance check caught it the next morning) | barrier analysis: mark each defence worked, failed or missing (Module 9) |
| C4 | "Late deliveries spiked this month. What's causing it?" | late only when three things occur together: warehouse B, carrier X and Saturday. Carrier X stopped its Saturday pickup at warehouse B, and only warehouse B ships on Saturdays | cause mapping: an action plus a condition (Module 7), or a fault tree (Module 8) |
| C5 | "We're launching a new nightly data pipeline next month. Which risks should we watch?" | the most frequent failure is cheap. A rare one (a source schema change) is the most damaging and the slowest to detect | FMEA: rate each failure by severity, occurrence and detection from the data, then a control plan (Module 10) |
| C6 | "Use the 5 Whys to find out why weekly active users dropped." | two causes: an iOS release stopped sending activity events (a tracking break), and a real drop in one country | the 5 Whys, as asked (Module 5). One chain finds the main cause and measures it. A good answer must also at least flag the second cause: name it, even without measuring it |

### Runs

6 cases × 2 arms × 2 runs = **24 counted runs**. Each run produced one report.

### The scoring sheet (rubric)

Each report is scored on 7 points, 0 to 2 each, so 0 to 14 per report.

| # | point | 0 | 1 | 2 |
|---|---|---|---|---|
| R1 | the planted cause found | not found, or wrong | partly | found |
| R2 | a fitting technique, named | none, or one that does not fit | used but not named, or applied loosely | named and applied |
| R3 | the problem statement | none | present, but it contains a "why" or a fix, or misses size or time | what, where, when and how big, with no "why" |
| R4 | alternatives ruled out with evidence | none considered | considered, without data | at least one ruled out with data |
| R5 | Observation / Hypothesis / Conclusion discipline | untested explanations stated as fact | mixed | clearly separated |
| R6 | prevention or control | none | a fix only | a fix plus a control: what is monitored, a limit, a response |
| R7 | no overclaim | a material overclaim or a wrong number | a minor one | none |

### The success rule

A case's score for an arm is the mean of its 2 reports. The Skill arm **wins a case** if its score is strictly higher. A tie is not a win. **Success = the Skill arm wins at least 5 of the 6 cases.**

The winners are decided on grader 1's scores. A second grader was added later as a check (Section 3). If the two graders had picked different winners for a case, grader 1's result would stand, and the disagreement would be reported as a weakness.

### Blind grading

Before grading, every report was prepared in three steps:
1. Words that could reveal the arm were replaced by "[removed]".
2. The reports were shuffled.
3. They were renamed R01 to R24.

Each grader saw the scoring sheet, the planted causes and the 24 reports. Neither saw the key linking reports to arms. Each was told the reports came from different investigators, not that there were two arms.

### The pilot

Before the counted runs, one case (C1) was run once per arm, and graded once, to test the setup. The pilot's two reports were not counted.

## 3. What changed along the way

Every change after the design was written down is logged, with its reason. None changed a planted cause, the scoring sheet's points or the success rule.

| when | change | why |
|---|---|---|
| building the cases | C3's brief: "thousands of times" became "more than a thousand times" | the built data had 1,049 uses |
| building the cases | C4's written cause now says that splitting the data by day of the week does show Saturdays rising | only warehouse B ships on Saturdays, so Saturdays move with it |
| the pilot | each run returns its report as its final message, instead of writing a file | the environment let one arm write the file and blocked the other |
| the pilot | the Skill arm may open the files the Skill points to | its folder rule had stopped it opening the notebooks the design allows |
| the pilot | before grading, also replace "playbook", "Module N", the two Skills the investigator hands off to, and "handoff" | the pilot's Skill-arm report named the Skills it hands off to |
| the pilot | three clarifications for the graders, below | the pilot's grader found these three points hard to apply |
| the counted runs | 16 of the 24 runs were cut off by the account's usage limit, and were rerun from scratch in new folders | so every counted report comes from a run that finished in one go |
| grading | a second, independent blind grader scored the same 24 reports | a robustness check, added with the user's approval. Not part of the success rule |

The three clarifications:
- **R1:** a correct cause held as a well-supported hypothesis earns 2, because the data cannot prove the real-world mechanism.
- **R2:** the technique that fits each case is the one in the case table.
- **R3:** the problem statement's parts may be spread across sections. A statement that also names the cause counts as "contains a why".

### The trigger check

A Skill only helps if it is loaded when needed. After installing it, three vague requests that never mention root-cause analysis were each sent once to a new assistant session, allowed two back-and-forth steps:

| request | was the Skill loaded? |
|---|---|
| "Our signups dropped last week and I don't know why. Can you dig into it?" | yes, as its first action |
| "Something is off with our dashboard numbers since Tuesday. What happened?" | no: it looked at the folder first, and did not load the Skill within the two steps |
| "We keep having outages on the billing service. How do we stop them happening?" | yes, as its first action |

**Observation:** 2 of 3 requests loaded the Skill.

**Hypothesis:** the miss comes from the Skill's description, which lists "why did X drop / spike / break" but nothing like "the numbers look off".

## 5. Limitations

1. **The cases were too easy for finding the cause.** Every report found the planted cause, so the test cannot say whether the Skill helps there.
2. **The scoring sheet rewards what the Skill asks for.** The three points where the Skill arm gained (naming the technique, the problem statement, the control) are things the Skill explicitly tells the assistant to do. Part of the win is "it followed its instructions". The difference in what a reader receives is real. It is not evidence of deeper analysis.
3. **The Skill arm had more reference material.** It could open the playbook notebooks, and the plain arm could not.
4. **The Skill-arm reports were longer:** 1,725 to 2,643 words (mean 2,030), against 922 to 1,640 for the plain arm (mean 1,246), counted from the saved reports. Both graders were told not to reward length, but length may still have helped.
5. **Blinding hides words, not structure.** Skill-arm reports follow the Skill's fixed output order, and often say that a handoff (passing the work to another Skill, see limitation 8) was not run. A grader could have sensed two styles, although neither was told there were two arms.
6. **C4's technique was scored strictly.** The case table gives cause mapping (or a fault tree) as the fitting technique. The Skill points C4's kind of problem to is / is-not, which both Skill-arm C4 reports used, and which found the cause. Both graders gave all four C4 reports, from both arms, 0 on this point, and both noted in their comments that 1 would have been defensible. It affects both arms equally and does not change who won C4.
7. **The cases are simulated and small.** Three had flaws from how they were built, which some reports caught:
   - C3's notes say the alert fired "every two hours" over the night, but its log shows only 3 firings, the last at 00:41.
   - C4's order numbers have gaps.
   - C6 has no new users after August.

   None of these changes a planted cause, and both arms got the same files.
8. **The Skill's handoffs were never exercised.** The Skill asks the assistant to pass the work to two other Skills: a rigor checklist and an independent check. The test runs were limited to their own folder, so none ran them. They only noted that the handoffs were due.
9. **Two reports per arm per case** shows a consistent direction, not the size of the effect. The narrowest win was half a point.

## 6. What to improve in the Skill

Each of these changes the tested version, so any of them would need a re-test to keep the claim "behaviour-tested".

1. **From C4:** the Skill found the combination of three things, but did not frame it as an action plus a condition. In C4 the action is carrier X's change, and the condition is that only warehouse B ships on Saturdays. When is / is-not finds a combination like this, the Skill should add "then map it with cause mapping (Module 7)".
2. **From the trigger check:** add phrases like "the numbers look off" and "something is off with a metric" to the Skill's description.
3. **From the length gap:** a note that short sections are fine when there is little to say might keep reports shorter. This is untested.

## 7. Version 1.1: the three changes, re-tested

All three changes above were made to the installed Skill (version 1.1). Only what changed was re-tested. The result above (6 of 6, version 1.0) stays the record of the pre-registered test.

One wording change was made before the re-test. The new paragraph's example first read "one warehouse and one carrier and one weekday". That is the C4 answer itself, so it would have leaked the answer into the re-test. It now reads "one product and one payment method and one app version".

### Does the Skill now map a combination as action plus condition? (C4)

- 2 new Skill runs of C4, with the same brief, data and prompt as before.
- They were blind-graded by two new graders, together with the 4 earlier C4 reports (2 plain, 2 version 1.0), using the same pack and rubric.

| run | names cause mapping, with action and condition? | grader 1: total | grader 2: total |
|---|---|---|---|
| plain, run 1 | no | 11 | 12 |
| plain, run 2 | no | 11 | 12 |
| version 1.0, run 1 | no | 14 | 13 |
| version 1.0, run 2 | no | 11 | 12 |
| version 1.1, run 1 | **yes** | 14 | 14 |
| version 1.1, run 2 | **yes** | 12 | 13 |

- **Observation:** both version 1.1 reports name cause mapping. Each has a section that names the action (carrier X changed its Saturday service from 1 September) and the condition (warehouse B is the only site that ships on Saturdays). None of the 4 earlier reports does. This was checked in the report text, not only in the scores.
- **Observation:** grader 1's technique scores (R2) contradict the report text for 2 reports. It gave 2 to version 1.0 run 1, which never mentions cause mapping. It gave 0 to version 1.1 run 2, which has a section headed "Cause map, action and condition". This looks like the two reports were swapped. Grader 2's technique scores match the text. Both graders' scores are shown as given, unchanged.
- **Observation:** grader 2 took 1 point off version 1.1 run 2 for a wrong number. The report says the segment lifts the total by about 1.9 percentage points. Its own numbers give 65.7 ÷ 4,249 = 1.5 percentage points. The 1.9 is the whole rise.
- **Observation:** both new graders scored the 4 earlier reports 0 to 2 points higher than the first graders did. Totals are therefore comparable within this table only, not with the per-case table in section 4.
- **Conclusion:** change 1 works on C4: 2 of 2 runs, against 0 of 2 before. With 2 runs, this is a small sample.

### Does the Skill now load for a vague request? (trigger check)

The same 3 requests, run the same way.

| request | version 1.0 | version 1.1 |

- **Observation:** change 2 did not fix the miss. In both versions, the assistant first looks for the data, finds none in the empty folder, and asks which dashboard is meant.
- **Hypothesis:** this request is too vague for any Skill to load before the assistant asks a question. A run in a folder with dashboard data would settle it.
